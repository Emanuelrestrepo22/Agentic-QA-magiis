Parte 0

Cómo aprender esto

El método WH y la escalera de 0 a experto. Léelo primero: es el sistema con el que vas a estudiar el resto del documento y con el que vas a trabajar cada día.

0.1 · El método WH (las preguntas que un QA senior siempre se hace)

Ante cualquier ticket, feature o bug, un QA con criterio no salta a "clickear". Primero se hace seis preguntas. Ese es el método WH. Aplicalo como checklist mental en cada etapa: si podés responder las seis, entendés el problema; si te falta una, ahí está el gap que tenés que cerrar (preguntando al PO/Dev o leyendo el contexto).

What
Qué

¿Qué cambió / qué se prueba? El feature, el AC, el endpoint, la entidad afectada.

Why
Por qué

¿Por qué importa? Regla de negocio, riesgo, impacto en el usuario o en el dinero.

Who
Quién

¿Qué rol/portal lo usa? Carrier, contractor, owner, pax, driver. Y qué rol lo dispara.

When
Cuándo

¿En qué etapa está el feature? (define Bug vs Defect). ¿Qué estados/transiciones cruza?

Where
Dónde

¿En qué capa vive la verdad? UI, API o DB. ¿Qué entorno? (default: UAT/staging).

How
Cómo

¿Cómo lo pruebo y cuánto? Técnica (EP/BVA/estados), trifuerza, y el ROI de automatizarlo.

Cómo se usa en el día a día

Abrís un ticket → recorrés las seis preguntas en voz alta (o en el chat) → las que no podés responder son tu lista de gaps. El agente te ayuda a responderlas leyendo el código y el contexto; vos validás y decidís. Ese recorrido ES el Shift-Left: pensar antes de ejecutar.

Regla de oro del aprendizaje

Una IA propone, el QA senior decide. El objetivo no es que el agente trabaje por vos, sino que vos aportes el criterio que el agente no tiene: negocio, riesgo y contexto. Subís de peldaño cuando dejás de preguntar "¿cómo se hace?" y empezás a preguntar "¿esto está bien probado?".

1.4 · Dev + QA = Definition of Done completo

Desarrollo ya usa un agente de IA (magiis-claude-agent) que audita el CÓDIGO (estático). Nosotros validamos el COMPORTAMIENTO. No se pisan, se complementan.

El valor que aporta QA

El code smell que QA no ve lo atrapa el audit; el bug de comportamiento/negocio/integración que el audit no ve lo atrapa QA. Juntos completan la Etapa 6 y el DoD al 100%. Nos montamos sobre lo que Dev ya construyó.

3.4 · Cómo aplicar la trifuerza, paso a paso

La trifuerza valida el mismo caso en 3 capas. Orden: UI primero (comportamiento), luego API y DB corroboran.

Capa 1 — UI (puerta de entrada funcional)

PasoQué hacésQué observás / criterio
1Abrir la app en UAT (apps-uat.magiis.com/carrier) y loguearte con el rol (ROLE_CARRIER)¿El login y el portal cargan para ese rol?

Criterio — capa UI

La pregunta es: ¿el comportamiento que ve el usuario coincide con el AC? Un mensaje de error crudo (ej. un 404 técnico) al usuario es un hallazgo aunque el dato termine guardándose.

Capa 2 — API (corrobora el contrato)

Criterio — capa API

La UI puede 'tapar' un error; la API muestra la verdad del contrato. Guardá SIEMPRE request + response como evidencia. Si el caso FALLA, el payload completo es obligatorio en el bug.

Capa 3 — DB (corrobora el estado real)

Solo cuando el caso muta datos. Se consulta Oracle (cliente externo / proyecto api-e2e) para verificar que el estado quedó consistente.

Qué revisásCriterio

Criterio — capa DB y cierre de la trifuerza

Un PASS de UI + API con la DB inconsistente sigue siendo un BUG. La trifuerza cierra solo cuando las 3 capas cuentan la misma historia. Recién ahí el caso es PASS de verdad.

3.5 · Análisis de la release — un ATP por feature (varios tickets)

A veces varios tickets pertenecen al MISMO cambio/feature: una Story de backend + una Story de frontend + un bug encontrado + un ticket de mejora. En ese caso NO se hace un ATP por ticket: se hace un solo ATP a nivel feature y un solo Test Execution que valida todos esos tickets juntos dentro de la release.

Artefacto XrayRol en la feature
Test PlanEl ATP de la feature (contenedor); agrupa lo de la release
Test SetAgrupación de los tests por feature / componente afectado
TestCada caso; se linkea (is tested by) al/los ticket(s) que cubre: Story BE, Story FE, Bug, Mejora
Test ExecutionEl ATR ÚNICO: una corrida que valida los N tickets de la feature
Criterio QA senior — el agrupamiento es tuyo

Vos decidís qué tickets forman una feature: mismo cambio funcional, mismo componente, dependencia BE-FE, o bug/mejora derivados de ese cambio. Un ticket independiente va en su propio ATP. El GO/NO-GO se evalúa a nivel FEATURE/RELEASE, no ticket suelto: un crítico abierto en cualquiera de los tickets del grupo bloquea la feature.

4.2 · Test Design Doctrine (cómo derivar casos de los AC)

La doctrina vinculante que gobierna qué probar. Es lo que separa "verificar" de "probar de verdad". Cárgala antes de derivar cualquier cobertura.

Los 5 principios

  • P1 — Verificar AC no es testing. Confirmar que la historia cumple sus AC valida el mínimo; "pasar" ≠ "probar". Parar en "todos los AC en verde" es quedarse en el happy path.
  • P2 — Los AC son el piso, no el techo. Cobertura real = conformidad-AC (piso) + riesgo-más-allá-del-AC (bordes, errores, estados, anomalías).
  • P3 — Criterio ≠ test case. El AC es una aserción de negocio (qué debe ser verdad); el test case es una exploración concreta (cómo eso aguanta o se rompe con datos/variantes/contexto).
  • P4 — Relación 1:N (explode-default). 1 AC → N test cases. El default es explotar (mínimo: partición válida + inválida + boundary). Colapsar a un solo caso exige justificación escrita ("trivially atomic").
  • P5 — El riesgo vive FUERA del criterio. Los defectos se agrupan donde el AC calla: boundaries, excepciones, concurrencia, orden, fallo de dependencia, timeouts, doble submit, rollback. Sin casos risk-beyond-AC, la cobertura está incompleta.

WH — cómo lo aplicás

What: el input/estado/condición del AC. How: elegís la técnica por su trigger. 4.4 · DoR / DoD — los contratos de entrada y salida

DoR-QA · entrada

Un ticket no entra a QA si no cumple:

  • Tipo claro + AC medibles en Given/When/Then (insumo #1 del ATP)
  • Mockup aprobado (UI) + validación multi-moneda/idioma/marca
  • Impacto: entidades/esquema, campos/migraciones, webhooks, endpoints, feature flag (probar ON/OFF)
  • Ambiente: build en qa/uat con flag ON + datos + rol/credenciales
DoD · salida (QA es dueño de "Pruebas")
  • Cobertura ≥ 80% código nuevo; unit + integración verdes en CI
  • QA funcional firmado; multi-moneda/idioma; multi-compañía (white-label)
  • Bugs críticos = 0, mayores ≤ 2
  • Feature flag documentado, migraciones aplicadas, plan de rollback, observabilidad
Regla de oro

Nada pasa a prod sin AC validado. Si UNA check del DoD falla, el ticket NO está hecho. "Hecho" = en producción, monitoreado, entregando valor.

8.3 · Por qué esto se repite en cada sprint

Este no es un caso especial: es EL loop de sprint del framework. Cambia el contenido de los tickets, pero los 10 pasos y la skill que los ejecuta son siempre los mismos. Por eso el criterio se vuelve un hábito.

Regla del loop

Un ticket suelto = los mismos pasos con 1 ATP en vez de uno de feature. Una release de 10 tickets = varios grupos de feature, cada uno con su ATP/ATR, y un GO/NO-GO consolidado. La forma no cambia; escala.
